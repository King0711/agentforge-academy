## Checkout recovery, Pro upgrade, email capture (added 2026-10-04)

Three revenue features, each with its own SQL file under `supabase/` (apply in this order — `checkout-recovery.sql` first, it widens the `email_log` type constraint the others rely on), then deploy the functions, then merge the frontend:

- **Checkout recovery** (`checkout-recovery.sql`, `send-abandoned-checkout-emails`): at most two emails per abandoned checkout (stage 1 at ≥1h, stage 2 at ≥24h), one candidate per person per run, nobody who already owns the product (`recovery_user_owns_plan`), only attempts from the last 72h. The cron job is *still named* `abandoned-checkout-daily` but now runs hourly during waking hours only (`20 7-19 * * *` UTC = 08:20–20:20 WAT, so nobody gets a reminder at 3 AM; pg_cron is UTC). It replaced a job that deduped per attempt (so repeat attempts = repeat emails) and kept emailing people who'd paid via a different attempt, because the webhook only resolves the attempt whose reference was paid. The recipient is `auth.users.email` (and only if confirmed) — **never `profiles.email`**: until `profiles-column-grants.sql` (PR #95, applied 2026-10-04) a user could rewrite their own `profiles.email` to a stranger's address and have reminders sent there. That is now closed at the source, but `auth.users.email` stays the canonical, confirmed address, so this job doesn't depend on that grant surviving (verified with a rolled-back simulation that rewrote every candidate's `profiles.email` as `postgres`, i.e. independent of the grants: 0 reminders went to the planted address). The same rule applies to any future job that emails "the account holder". `PRODUCTS` in the function holds the per-plan copy and links — every claim there must already be on the product's own page. The AI Agent Mastery next-cohort line is a *third* copy of the weekly arithmetic (`FIRST_START_UTC`); keep it with `src/data/aiMasteryCohort.js` and `send-aimastery-class-reminders`. `email_log` now accepts `welcome` (the webhook has always written it; every audit row used to fail the constraint silently), `lead_confirm`, `lead_drip`.
- **Pro upgrade-by-difference** (`pro-upgrade.sql`): plan key `proupgrade` (no underscore — checkout references are `sdt_<plan>_<uuid>_<ts>` and the backfill script splits on `_`). Owns Builder 1 → pays ₦5,000 (`PRO_PRICE - BUILDER1_PRICE`) and gets Builder 2; owns Builder 2 → pays ₦3,000 and gets Builder 1. `create-paystack-checkout` decides the price from the caller's `guide_purchases` rows (never the client) and refuses owns-neither (403) / owns-both (409); `paystack-webhook` re-derives ownership and the expected amount before granting, and records `payments.plan = 'pro'` (the end state) at the amount actually paid — no payments/referral constraint changes. Mismatches land as `flagged_upgrade_not_applicable` (user_id set) for manual refund. The upgrade table is derived from `PRICES` in both functions and from `BUILDER*_PRICE`/`PRO_PRICE` in `src/data/pricing.js`, so a price change flows through. Grandfathered subscribers (entitlement only, no `guide_purchases`) are not offered it. UI: `useUpgradeOffer` + `UpgradeOfferCard` (dashboard) + `UpgradeButton` on `Pricing.jsx`; the welcome email for single-tier buyers carries the same offer.
- **Email capture + starter series** (`email-capture.sql`, `email-leads` function, `EmailCapture`, `SubscribeStatus`): double opt-in; `email_subscribers` has RLS on with no policies and no anon/authenticated grants — everything goes through the function (service role). **Deploy `email-leads` with `verify_jwt = false`.** Cron `lead-drip-hourly` (`40 7-19 * * *` UTC, waking hours WAT) sends drip steps 2 and 3 at +2 and +5 days from confirmation; step 1 is sent by the confirm action itself (retried by cron if that send fails). Subscribers who match an account with a granted payment are marked `converted_at` and skipped. Kill switch: `email_settings.lead_drip_automation_enabled` (SQL only — the admin UI doesn't expose it). Flood guard: at most 60 confirmation emails per rolling hour *including re-sends* (an earlier draft only capped new addresses, which left re-sends as a bypass), and addresses that never confirm are deleted after 30 days by the hourly run. The confirm/unsubscribe pages act only on a button press because mail scanners pre-open links. **Emails deliberately don't invite replies and carry no `mailto:`**: as of 2026-10-04 the apex domain has no MX record, so a reply to `notifications@` or mail to `support@socialdevtechnologies.com` bounces (re-verify with DNS-over-HTTPS before relying on it); the emails point to WhatsApp (`wa.me/2349066006963`, replies 10am–5pm WAT Mon–Sat) instead. If an MX / email-routing setup is added, those lines can go back. Other functions' footers (webhook welcome, winback, reminders) still say "Reply to this email or contact support@" — same problem, not touched here. The step-3 email quotes ₦5,000/₦7,000/₦10,000 as literals in `email-leads` — a *fifth* place to move with a repricing (alongside `pricing.js`, `paystack-webhook`, `create-paystack-checkout`, the WhatsApp `knowledge-base.ts`). The free lead magnet is the existing public `/session/daily-news-agent` walkthrough.
- Funnel numbers: `select * from admin_get_lead_funnel()` (as an admin) or query `email_subscribers` directly.

## Discount codes (added 2026-10-16, AI Agent Mastery only)

Admins generate codes at `/admin/discount-codes` (`AdminDiscountCodes.jsx`; count, uses per code, optional expiry, note); a buyer types one into `CouponField` on the `/ai-agent-mastery` price card and pays `DISCOUNT_CODE_PRICE_NAIRA` (10,000 — a constant in both `create-paystack-checkout` and `paystack-webhook`, keep them together). `supabase/discount-codes.sql` (`discount_codes`, `discount_code_redemptions`; RLS on, no client grants; admin RPCs gated with `admin_session_ok()`). Codes are random `XXXXX-XXXXX` (50 bits, from `gen_random_uuid()`), so the unauthenticated `validate_coupon` action in `create-paystack-checkout` is not practically guessable. Checkout re-validates the code (the card's "Apply" is display only), takes precedence over the scholarship price, and puts `coupon_id` in the signed metadata; the webhook calls `redeem_discount_code` only after the granted payment (idempotent per payment reference). Known gap: a single-use code is counted at payment, not reserved at checkout, so two people holding the same code could both pay the discounted price before either completes. Deploy order: SQL, then both functions, then the frontend. To extend to other courses: widen the `plan` check, add a per-code price, and teach `lookupDiscountCode`/the webhook's amount list about it.

## Guest checkout + lead capture (added 2026-10-13)

Signed-out visitors pay **before** they have an account (founder direction 2026-10-13: "pay first, verify at first login"; phone required with a chosen country code). `CheckoutAuthModal` (name / email / phone form; the file kept its old name because every checkout surface renders it) → `usePaystackCheckout().submitLead` → `create-paystack-checkout` with `body.lead` and no user JWT. SQL first (`supabase/guest-checkout.sql`: `checkout_leads`, `profiles.phone`, `admin_list_checkout_leads`), then deploy `create-paystack-checkout`, `paystack-webhook` and the new `guest-checkout-status`, then merge the frontend. Old frontend + new functions is safe (signed-in checkout is unchanged); new frontend + old functions is not (guests get a 401).

- **Guest path in `create-paystack-checkout`:** validates the lead (name, email, E.164 phone; honeypot field `website`), rate-limits per IP hash (20/h) and globally (400/h), inserts a `checkout_leads` row *before* charging (so abandoned buyers stay on the list), and charges with `metadata.lead_id` instead of `user_id`; the reference is `sdt_<plan>_<LEAD uuid>_<ts>`, callback `/checkout/complete`. Guests can't buy `proupgrade` (needs their purchase history) and never get the scholarship price (needs a confirmed email) — both stay signed-in-only. No `checkout_attempts` row for guests (that table needs a user), so the checkout-recovery emails don't reach them; `/admin/leads` (WhatsApp links + CSV export) is how an abandoned guest gets followed up.
- **Account creation is in `paystack-webhook` (`resolveGuestBuyer`), only after the signature and amount checks pass.** It finds the account for the lead's email through `profiles.email` or creates one with `auth.admin.createUser({ email_confirm: false })`, passing `display_name` and `referral_code` as user metadata so `handle_new_user` creates the referral row before commission is computed. It fills a *missing* `profiles.phone` and links the lead (`user_id`, `paid_at`). A failure returns 404 so Paystack retries. An existing account is matched by email and gets the purchase — a stranger typing someone's address can only gift them a product, never read anything. No non-payer ever becomes an auth user.
- **First login = email verification:** `/checkout/complete` (`CheckoutComplete.jsx`, noindex) polls `guest-checkout-status` (public; answers only plan/amount/currency for an already-granted reference), fires the Meta `Purchase` event (shared `trackPurchase` in `src/lib/pixel.js`, deduped by reference), then sends a login code with `sendLoginCode` and verifies it with `verifyLoginCode` (`verifyOtp` type `email` also accepts the unconfirmed-account code). The welcome email for guests explains the same steps. If a future change turns on `shouldCreateUser:false` problems for unconfirmed accounts, that is the first place to look.
- **Phone:** `src/data/countryCodes.js` (193 countries, Nigeria default; `buildE164` accepts 0-prefixed, `+`-prefixed and dial-prefixed input). The server re-validates `^\+[1-9][0-9]{7,14}$`. `profiles.phone` is server-only (not in the client grant) by design.
- **Lead follow-ups + WhatsApp leads (2026-10-24, `supabase/lead-followups.sql`):** `checkout_leads` gained `source` (`checkout` / `whatsapp_form` / `whatsapp_manual`) and `email` is now nullable (WhatsApp leads often have only a phone; nothing that pays reads a lead without an email). `lead_followups` logs how a call went plus a next action and date, stamped with the admin who entered it; `/admin/leads` shows the log per lead and a "My next actions" list, with Google Calendar link and `.ics` download (`src/lib/calendarLinks.js`) — not a live calendar sync, that would need Google OAuth or a per-admin feed. The WhatsApp button's form (now asks for a number) calls the public `capture-whatsapp-lead` function (`verify_jwt = false`, honeypot, per-IP/global caps, same phone within 24h = one lead). Admins add leads by hand with `admin_add_checkout_lead`. Deploy order: SQL, `capture-whatsapp-lead`, frontend. `admin_list_checkout_leads` changed shape (adds `source`), so the old frontend still works against the new SQL but new frontend needs it.
- Untested end to end against live Paystack as of the PR: do one real test purchase, and check the new user appears in Auth as unconfirmed, then confirmed after the code login.

## Admin analytics (added 2026-10-24)

`/admin/analytics` (`AdminAnalytics.jsx`, charts in `src/components/admin/analytics/`): revenue today / week / month / year against the same point in the previous period, a revenue-by-product trend, page views and unique visitors, a visitor -> checkout -> paid funnel, new accounts, and top pages / sources / devices / countries, filtered by day range and grouped daily, weekly, monthly or yearly. `supabase/admin-analytics.sql` holds six `admin_*` RPCs (standard three-revoke + `admin_session_ok()`). Days are Africa/Lagos calendar days. Revenue is `payments` rows whose status starts with `granted`, at the amount Paystack charged (includes any passed-on card fee, before referral commission).

**Traffic is first-party and only exists from the day it shipped.** The database had no traffic data (Google Analytics holds it, nothing here can read it). `src/lib/visits.js` (called from `AppShell` in `App.jsx`) posts one beacon per page view to the public `track-visit` function (`verify_jwt = false`) which writes `site_visits` (RLS on, no grants). It stores path, a source reduced to a channel, device class and keyed hashes of a random localStorage browser id and of the IP (rate limit only: 120/min). No cookies, no raw identifiers. It counts only `socialdevtechnologies.com` and skips `/admin`, bots, `navigator.webdriver` (the prerender) and localhost/previews. Sources count only the first page of a session (`is_entry`), since `document.referrer` doesn't change on SPA navigation. A weekly cron prunes rows older than 800 days. **Deploy order:** SQL, `track-visit`, then merge the frontend; the beacon is fire-and-forget (`no-cors`, `text/plain` so there is no preflight), so a missing function only means no data. Backfilling history would need the GA4 Data API and a service account owned outside the repo.

## Admin two-step verification (added 2026-10-13)

TOTP (authenticator app) for admin accounts, enforced in the **database**, not just the UI. `supabase/admin-mfa.sql`: `admin_security_settings.require_mfa` (the switch, **ships off**), `admin_session_ok()` (true when the switch is off or the JWT's `aal` claim is `aal2`; SECURITY INVOKER so it works inside policies for any role), a rewrite of **all 50 `admin_*` functions** so their inline admin check also calls it (the migration regex-patches `pg_get_functiondef` output and aborts if any admin function has an unrecognised check — a new `admin_*` RPC must put `and public.admin_session_ok()` next to its `is_admin = true` check, or the final proof block in that file will fail on the next re-run), and the admin-only table/storage policies (`ai_models`, `ai_platform_settings`, `cohort_schedule` update, `community_messages` delete-any, `course_content_draft`/backup, the three `news-images` policies). Verified in a rolled-back transaction with simulated JWTs: switch off + aal1 admin = works; switch on + aal1 = "Unauthorized"; switch on + aal2 = works; non-admin refused either way.

## CORS (audited 2026-09-27)

Every browser-facing Edge Function restricts `Access-Control-Allow-Origin` to `socialdevtechnologies.com` / `*.vercel.app` / `localhost:*` via a per-file `ALLOWED_ORIGIN_PATTERNS` + `corsHeadersFor(req)` helper (duplicated per function, not shared — check each one individually if changing the allow-list). `ai-gateway` was the one exception (`Access-Control-Allow-Origin: '*'`) — tightened to the same pattern. It's still safe for student Python scripts hitting it via `X-SDT-Key`: CORS is a browser-only mechanism, and a script never sends/enforces an `Origin` header, so restricting it only affects browser callers from *other* origins, not the intended script path. `vercel.json` also gained `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin` (the existing CSP/HSTS/X-Frame-Options/COOP were already in place and already allow `wss://*.supabase.co` for the community feature's Realtime).

**Every new `admin_*` RPC needs three revokes, not one.** The internal `is_admin()` guard is necessary but isn't the whole job — two separate default-grant mechanisms make a fresh function reachable anonymously over `/rest/v1/rpc/<name>` unless both are revoked:
1. Postgres grants `EXECUTE` to `PUBLIC` by default on `CREATE FUNCTION`, and `anon`/`authenticated` inherit from `PUBLIC`.
2. This Supabase project's `ALTER DEFAULT PRIVILEGES` on the `public` schema *also* grants `EXECUTE` directly to `anon` (and `authenticated`), independent of `PUBLIC` — confirmed 2026-08-19 when `admin_update_testimonial` came out of `CREATE FUNCTION` with `anon` already in its ACL despite no explicit grant statement. Revoking only `FROM PUBLIC` leaves this direct grant untouched.

Ship every admin RPC with all three statements:

```sql
REVOKE EXECUTE ON FUNCTION public.<name>(<arg types>) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION public.<name>(<arg types>) FROM anon;
GRANT  EXECUTE ON FUNCTION public.<name>(<arg types>) TO authenticated;
```

A correctly-locked function's ACL reads `postgres=X, authenticated=X, service_role=X` with no leading `=X/postgres` entry (that empty grantee is `PUBLIC`) and no `anon` entry — check by querying `aclexplode(proacl)`, not just by eyeballing `REVOKE ... FROM PUBLIC` in the migration. The guides-CMS and live-session RPCs shipped without any of this and were anonymously callable until 2026-08-19; the `is_admin()` guard did hold, so nothing was exposed, but they were relying on a single layer. Check with `get_advisors(type: "security")`.

`get_certificate_by_id` is deliberately left callable by `anon` — the public `/verify/:id` page depends on it.

## Pentest follow-up (2026-10-04)

A Pentest-Tools light scan reported only false positives/generic warnings, but the review behind it changed these:

- **`profiles` is column-granted** (`supabase/profiles-column-grants.sql`): clients may update only `display_name` and `industry`, and can't insert (`handle_new_user()` creates rows). RLS limited users to their own row but not to columns, and `paystack-webhook` resolves pay-first and manual-charge buyers by `profiles.email` — so a user-writable email let anyone divert a BYU student's purchase to their own account (never exploited; audited first). A new `profiles` column is server-only unless it's added to that grant — keep it that way for anything server code trusts.
- **Scanner probes no longer get the homepage.** The SPA catch-all in `vercel.json` excludes dot-paths (`/.env`, `/.git/…`, unknown `/.well-known/*`), `/wp-*` and `*.php|asp|aspx|jsp|cgi`. In production, dot-paths get Vercel's plain 404, but WordPress/PHP paths get a 403 from Vercel's firewall (`x-vercel-mitigated: deny`, for every client) — that's expected, not a routing bug. Don't verify this with a quick curl loop from one machine: a burst of probe-like requests gets that IP challenged (`x-vercel-mitigated: challenge`), and then even its `/assets/*.js` requests 403 for a while, so the site looks broken from there only. - **Server-rendered `api/*` pages:** JSON-LD goes through `jsonLdBody()` (`src/lib/jsonLd.js`) — `JSON.stringify` alone lets a `</script>` in a title end the element — news `source_url`/`image_url` must parse as http(s), and `applyOgImage()` escapes the image URL.

- **`public/.well-known/security.txt`** expires 2027-10-01 — RFC 9116 wants `Expires` under a year out, so bump it before then. Its contact is `support@`, which needs a working MX record to receive mail.

## Article and guide images

Header images for news articles and guides live in the **`news-images` Supabase Storage bucket** (public), but `image_url` on a row stores a **first-party URL**, never the raw storage one:

```
https://socialdevtechnologies.com/article-images/<slug>-<timestamp36>.jpg
```

`vercel.json` rewrites `/article-images/*` onto the bucket's public endpoint — so images are attributed to the site rather than a `supabase.co` host, and changing storage later is a rewrite change instead of a rewrite of every `image_url` in the database. The rewrite must stay **above** the catch-all `/(.*)  → /index.html`, or it never matches. `src/lib/articleImages.js` owns the path/URL construction; keep it and the rewrite in step.

**Use 1200×675 (16:9).** Every on-site placement renders the image in a 16:9 `object-cover` box — both listing cards (`News.jsx`, `GuidesIndex.jsx`) and both article heroes (`NewsArticle.jsx`, `GuidePage.jsx`) — so 1200×675 fits all four exactly, while still clearing LinkedIn's 1200×627 floor for the `og:image` (which crops to ~1.91:1 and loses only a couple dozen pixels). The admin upload control warns on off-ratio images but never blocks them.

**Uploads use a unique path per upload, not a stable `<slug>.jpg`.** These are served with a one-year immutable `Cache-Control`, so overwriting a path would strand viewers on the old image until the CDN entry expired. The tradeoff is that replaced images become unreferenced orphans in the bucket — prune them from the Supabase dashboard, not with `delete from storage.objects` (a direct row delete unlinks the index entry but leaves the actual blob behind).

**Storage policies are a separate layer from the `admin_*` RPC grants above.** The bucket existed with *zero* RLS policies until 2026-08-22 and nobody noticed, because `generate-news-digest` writes through `service_role`, which bypasses RLS entirely — so the gap only surfaced when a browser first tried to upload. Anything that writes to a bucket from the client needs explicit policies; `supabase/article-images-setup.sql` holds the three admin-gated ones (insert/update/delete) plus the bucket's `file_size_limit` (2MB) and `allowed_mime_types` (JPG/PNG/WebP). Those two bucket settings were also null until then — harmless while only `service_role` could write, dangerous the moment a browser can.

Note the policies read the caller's `entitlements` row, which works only because that table's RLS permits `auth.uid() = user_id` self-reads. Tightening `entitlements` RLS would silently break admin uploads — verify with a role-simulation probe (`set local role authenticated` + `request.jwt.claims`), not by eyeballing the policy.

**Automatic generation exists but has never run.** `generateImage()` in `supabase/functions/generate-news-digest/index.ts` calls OpenAI `gpt-image-1` when `OPENAI_API_KEY` is set, and returns `null` (logging a warning) when it isn't — which is why the bucket sat empty for weeks. Two things to know before switching it on: `gpt-image-1` is **deprecated as of 2026-10-23**, and the hardcoded `1536x1024` is 1.5:1, not the ~1.91:1 the code comment claims to be aiming for. Gemini's free tier (~500 images/day, native 16:9) was evaluated as the better replacement if per-article art is ever wanted.

## Prerendering never supported hydration — don't reintroduce `hydrateRoot`

`scripts/prerender.mjs` snapshots a **live, animating** page. framer-motion writes inline styles continuously, so whatever frame Puppeteer happened to catch gets baked into the committed snapshot — e.g. `public/prerendered-home.html` verifiably contained `style="opacity: 0; transform: translateX(0.55724px) translateY(0.222896px);"`. That's a mid-flight animation frame; React's first client render emits the component's `initial` styles instead, which can never match those sub-pixel numbers. Result: `hydrateRoot` fails with React #418 on every visit to any prerendered route using `m.*` (framer-motion) elements, and React responds by discarding the *entire* prerendered tree and rebuilding it client-side.

This was fixed once (2026-08-19, measured LCP 532→400ms, TBT ~218→151ms, console #418→clean) by making `src/main.jsx` always use `createRoot`. It was reverted minutes later with no recorded reason, silently erasing this note along with it — which is exactly how the regression went unnoticed until it surfaced again as a **Google Search Console soft-404 on `/vibe-coding`** (2026-09-16): the raw served HTML is fully populated (verified directly), but Googlebot's rendering pass executes the same JS a real visitor does, and catches the page mid-teardown/rebuild — sometimes before `useAuth`/`usePro`/`useCohortSchedule` resolve — which can look thin enough to trip the soft-404 heuristic. The homepage has the same animation pattern and almost certainly has the same defect; it just hasn't been flagged in GSC yet.

**Prerendered snapshots carry their own CSS (2026-09-28).** Each `public/<route>/index.html` from `npm run prerender` inlines the Tailwind CSS from the day it was snapshotted, but loads the always-current `/assets/index.js`, and Vercel serves that static file before any rewrite. A class added to a component after the snapshot therefore didn't exist on that route in production. That's how `/ai-agent-mastery` (snapshot from 09-22) lost its flow-diagram and instructor-card colours. `scripts/inline-css.mjs` now swaps this build's CSS into every snapshot in `dist/` at build time. To reproduce a route as production serves it, use `node scripts/static-serve.mjs dist`, not `vite preview`: `vite preview` falls back to the homepage shell with fresh CSS and hides this class of bug. The snapshots' *body markup* can still be stale (SEO/first paint only, since React replaces it), so re-run `npm run prerender` after large page changes. Anything that computes a date or time in the browser is baked into the snapshot as of the moment Puppeteer ran, unless its element carries `data-client-only` (the prerender strips those) — that is why the AI Agent Mastery page says "Friday" instead of a date. To regenerate from a clean worktree, pass the public `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` as environment variables (never on disk) or cohort/testimonial data bakes in empty.

Re-applied the `createRoot`-always fix in `src/main.jsx` on 2026-09-16. **Re-running `npm run prerender` does not fix this** — it just bakes a different random animation frame. `hydrateRoot` only becomes viable again if mount animations are dropped from prerendered routes, making the first client render deterministic. Until then, `createRoot` is correct, not a workaround — if you're tempted to revert this again, fix the animation-snapshot mismatch first, or at minimum re-run `npm run prerender` + Puppeteer content-length checks against every route in `scripts/prerender-routes.mjs` before merging, and leave a reason in the commit this time.
